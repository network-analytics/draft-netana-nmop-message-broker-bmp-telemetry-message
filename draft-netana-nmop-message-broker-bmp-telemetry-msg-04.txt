         draft-netana-nmop-message-broker-bmp-telemetry-msg-04

Abstract

   This document defines an extensible message schema in YANG to be used
   at BMP collectors to transform BMP messages into messages which are
   consumed by external systems such as Message Brokers.

1.  Introduction

   Nowadays network operators are using BGP Monitoring Protocol (BMP)
   [RFC7854] to monitor the BGP peerings and RIB's.  With
   [I-D.ietf-nmop-message-broker-telemetry-message] a machine and human
   readable extensible Network Telemetry message schema in YANG
   [RFC7950] has been defined.

   Network operators organize their data in a Data Mesh [Deh22] where a
   Message Broker such as Apache Kafka [Kaf11] or Apache Pulsar [Pul16]
   facilitates the exchange of messages among data processing
   components.

   YANG Message Keys for Message Broker Integration
   [I-D.ietf-nmop-yang-message-broker-message-key] describes how
   Dimensional YANG data can be indexed and addressed in Message
   Brokers.

   This document describes how
   [I-D.ietf-nmop-message-broker-telemetry-message] defined Network
   Telemetry message is being extended to support BMP data
   transformation to YANG at the BMP Network Telemetry data collector
   and being indexed and addressed in Message Broker based on
   [I-D.ietf-nmop-yang-message-broker-message-key] principles at the
   YANG Message Broker Producer.

   [I-D.ietf-nmop-yang-message-broker-integration], and using the 'ietf-

   YANG-Push specific subscription metadata.

   This document defines five BMP YANG modules Section 7.1, Section 7.2,
   Section 7.5, Section 7.6, Section 7.7 and two BGP YANG modules
   Section 7.4, Section 7.3.  The 'ietf-bmp-message' module, together
   with the modules it imports, defines the BMP messages, which can be
   used on their own or populate the anydata "payload" node defined in
   the 'ietf-telemetry-message' YANG module of
   [I-D.ietf-nmop-message-broker-telemetry-message].  The 'ietf-bmp-

   the same way as 'ietf-yang-push-telemetry-message' does for YANG-

4.  Carrying BMP Messages in Network Telemetry Messages

   A BMP message modeled by 'ietf-bmp-message' can be published to the
   Message Broker on its own, forming the Message Value, or carried in
   the "payload" of a Network Telemetry Message defined by the 'ietf-
   telemetry-message' module of
   [I-D.ietf-nmop-message-broker-telemetry-message], which then forms
   the Message Value.  The Network Telemetry Message adds metadata about
   the network node, the data collector, and the BMP session, such as
   the session-start-timestamp and the cached Initiation information,
   that a BMP message on its own does not carry.

   When a Network Telemetry Message is used, its nodes other than
   "payload" carry two kinds of metadata:

   *  Nodes defined by 'ietf-telemetry-message' for any Network
      Telemetry protocol.  Section 4.1 defines how they are populated
      for BMP.





Graf, et al.              Expires 26 April 2027                 [Page 7]

Internet-Draft     BMP YANG Network Telemetry Message       October 2026


   *  BMP specific nodes defined by this document in 'ietf-bmp-
      telemetry-message', described in Section 4.2.

5.  YANG Message Broker BMP Indexing and Topic Naming

   To identify which network node produced which BMP data into which
   Message Broker Topic, Partition and Subject, BMP Message Keys,
   Partition Key, and Indexes are being introduced (Section 5.1).  These
   keys enable a deterministic distribution of BMP messages across
   Topics and Partitions enabling applications to consume only the
   needed data from specific topics and partitions.

5.1.  BMP Message Keys and Indexes

   A Message Broker uses a Message Key for indexing and enabling Topic
   Compaction.  While a Message Key can also drive deterministic
   partition assignment, this document introduces a dedicated Partition
   Key for that purpose, as described in Section 5.2.

   Similar to Section 3.1 of
   [I-D.ietf-nmop-yang-message-broker-message-key] for YANG-Push
   telemetry messages, the network node hostname and a set of 'ietf-bmp-
   message' YANG nodes from the instance data are used to construct the
   BMP Message Key. The following subsections describe and illustrate
   the YANG nodes used for each BMP message type.

   For all BMP message types that carry a BMP Per-Peer Header (Peer Up,
   Peer Down, Statistics Report, Route Monitoring, and Route Mirroring),
   the Message Key consists of the node hostname and a YANG instance-
   identifier path encoding the message-type and the following per-peer
   header nodes to uniquely identify the BGP peering session:

   peer-type
      Scopes the session to its routing instance: Global Instance Peer,
      RD Instance Peer, Local Instance Peer, or Loc-RIB Instance Peer.






Graf, et al.              Expires 26 April 2027                [Page 12]

Internet-Draft     BMP YANG Network Telemetry Message       October 2026


   peer-distinguisher
      The Route Distinguisher of the routing instance.  Zero-filled for
      Global Instance Peers; non-zero for RD Instance and possibly Loc-
      RIB Instance Peers to distinguish sessions within the same VRF or
      routing instance.

   peer-address
      The remote IP address associated with the BGP session.

   peer-as
      The AS number of the remote BGP speaker.

   peer-bgp-id
      The BGP Identifier of the remote BGP speaker.

   Route Monitoring and Route Mirroring messages extend the per-peer
   session key with two additional YANG nodes that identify the
   individual route within the RIB:

   prefix
      The IP prefix (IPv4 or IPv6) of the route entry.

   path-id
      The BGP ADD-PATH path identifier ([RFC7911]).  Zero when ADD-PATH
      is not in use.

   Initiation and Termination messages do not carry a Per-Peer Header;
   their Message Keys consist of only the node hostname and the message-
   type path.  The per-peer session key is consistent across all
   lifecycle events for the same session (Peer Up, Statistics Report,
   Route Monitoring, and Peer Down), enabling deterministic topic
   compaction over the full session lifecycle.  The session-start-
   timestamp of the bmp-session container is not part of the Message
   Key, so that the key remains the same when a BMP session is re-
   established.

   The Message Key is encoded as a two-line byte string.  The first line
   is the network node hostname; the second line is the YANG instance-
   identifier path.  The separator between them is a single line feed
   character (LF, U+000A).  The YANG path starts at the 'ietf-bmp-
   message' message node, whether the BMP message is the Message Value
   itself or is carried in the "payload" of a Network Telemetry Message
   (Section 4).  The Message Key is therefore the same in both cases.  A
   path through "payload" is not used, as "payload" is anydata and its
   content is not part of the 'ietf-telemetry-message' schema.

5.2.  BMP Partition Keys and Routing

   Since BMP requires Message ordering for a monitored BGP RIB, and
   Message Brokers ensure Message ordering on partitions, a Partition
   Key and a custom partitioner logic is being introduced so that all
   BMP messages for a particular BGP RIB are hashed to on one partition.
   The Partition Key consists of the hostname of the network node.



Graf, et al.              Expires 26 April 2027                [Page 26]

Internet-Draft     BMP YANG Network Telemetry Message       October 2026


   In the partitioner implementation of the YANG Message Broker
   Producer, instead of the Message Key, the Partition Key MUST be used
   to deterministically hash BMP Messages to partitions.

5.3.  Message Broker BMP Topic Naming

   There are two Message Broker topics.

   *  bmp-state-changes-and-statistics: Containing all BMP messages in
      real-time

   *  bmp-current-state: Containing all BMP message types, except
      statistics, topic compacted.

   Optionally, an organization prefix can be prepended with a "-"
   separator.  A Message Broker Consumer MAY consume either "bmp-state-
   changes-and-statistics", "bmp-current-state" or a subset depending on
   use case.

   If a subset is consumed, the consumer hashes the Message Key, applies
   modulo with the number of partitions, and determines the partition
   from which it should consume messages bearing that Message Key.

   To parse the Message Key, the consumer splits the byte string on
   newline (LF) characters.  The first line is the node-name and the
   second the YANG path.

   Figure 15 shows an example where "bmp-state-changes-and-statistics"
   is being used.

   netops-bmp-state-changes-and-statistics

                     Figure 15: BMP Topic Name Example

6.  Message Broker Implementations

   Topic, Partitioning and Message Keys are generic concepts of Message
   Brokers.  There are two known Message Broker implementations
   supporting all features described in this document.

6.1.  Apache Kafka

   Apache Kafka supports Message Keys, Partitioning and Log Compaction.
   Per default, the partitioner logic uses Message Keys for
   deterministic partition Message distribution.






Graf, et al.              Expires 26 April 2027                [Page 27]

Internet-Draft     BMP YANG Network Telemetry Message       October 2026


   This document introduces "partition-key" in the Apache Kafka header
   to be used by the partitioner instead of the "key" (Message Key) when
   distributing Messages to the partitions.

6.2.  Apache Pulsar

   Apache Pulsar supports Message Keys, Partitioning and Topic
   Compaction.  Per default, the partitioner logic uses Message Keys for
   deterministic partition Message distribution.  Optionally, a
   dedicated ordering key can be used.

   This document introduces "partition-key" which is to be used as
   ordering key.

7.  BMP YANG Modules

   The 'ietf-bmp-message' YANG module defines the top-level BMP message
   structure.  It does not depend on 'ietf-telemetry-message': a BMP
   message can be used on its own or carried in the "payload" of a
   Network Telemetry Message (Section 4).  It carries a mandatory
   version leaf from the BMP Common Header and a message-type choice
   covering all seven BMP message types: route-monitoring, statistics-
   report, peer-down-notification, peer-up-notification, initiation-
   message, termination-message, and route-mirroring-message.

   The 'ietf-bmp-peer-header' module provides the peer-type typedef and
   the peer-header-flags grouping decoded from the BMP Per-Peer Header.
   It is imported by both 'ietf-bmp-message', for the per-peer header
   itself, and 'ietf-bmp-tlv', for the Extended Flags TLV, which extends
   the same flag bits to a variable-length byte sequence.

   The 'ietf-bmp-statistics' module provides the statistics grouping
   used by statistics-report messages.  Each Stat Type of the IANA 'BMP
   Statistics Types' registry ([RFC7854] ,[RFC8671], and [RFC9972]) is
   modeled as a named data node, for example routes-in-loc-rib, whose
   YANG type reflects the encoding of its Stat Data.  Because a new Stat
   Type requires a new node, and thereby a module revision, a catch-all
   unknown list carries Stat Types that are not yet modeled, or whose
   Stat Data cannot be decoded, as raw binary, so no statistic has to be
   dropped.











Graf, et al.              Expires 26 April 2027                [Page 28]

Internet-Draft     BMP YANG Network Telemetry Message       October 2026


   The 'ietf-bgp-rib-entry' module provides the rib-entry grouping used
   by route-monitoring and route-mirroring messages.  It selects between
   five RIB table types — loc-rib, adj-rib-in-pre, adj-rib-in-post, adj-
   rib-out-pre, and adj-rib-out-post — via a nested rib-type choice.
   Each route entry contains the prefix, optional path-id for ADD-PATH,
   BGP path attributes, and community attributes.  Instead of a route, a
   rib-entry can carry an end-of-rib marker, which represents the End-
   of-RIB marker (Section 2 of [RFC4724]) for the AFI/SAFI given by afi-
   safi-type.

   The 'ietf-bgp-open' module provides the bgp-open grouping, which
   carries the BGP OPEN message fields: protocol version, Autonomous
   System number, hold time, BGP identifier, and the negotiated
   capability list.  It is used in peer-up-notification for both the
   sent and received OPEN messages.

   The 'ietf-bmp-tlv' module provides groupings for the decoded content
   of BMP TLVs.  The common grouping (sequence number, timestamps,
   extended flags, and an unknown-tlvs catch-all for TLV types not yet
   modeled) is used by all seven BMP message types.  The other groupings
   are each specific to one message type: Initiation, Peer Up (including
   the Admin Label TLV of [RFC9736]), Termination, Peer Down, and Route
   Monitoring.

   The 'ietf-bmp-telemetry-message' YANG module extends 'ietf-telemetry-
   message' for BMP.  It defines the bmp identity, derived from session-
   protocol, and augments telemetry-message-metadata with the bmp-
   session container, which carries the BMP session metadata maintained
   by the data collector.  Its use is described in Section 4.2.

9.  Security Considerations

   This section is modeled after the template described in Section 3.7
   of [I-D.ietf-netmod-rfc8407bis].

   The "ietf-bmp-message", "ietf-bmp-telemetry-message", "ietf-bgp-rib-
   entry", "ietf-bgp-open", "ietf-bmp-tlv", "ietf-bmp-peer-header", and
   "ietf-bmp-statistics" YANG modules define one combined data model
   that is designed to be accessed via YANG-based management protocols,
   such as NETCONF [RFC6241] and RESTCONF [RFC8040].  These protocols
   have to use a secure transport layer (e.g., SSH [RFC4252], TLS
   [RFC8446], and QUIC [RFC9000]) and have to use mutual authentication.

   The Network Configuration Access Control Model (NACM) [RFC8341]
   provides the means to restrict access for particular NETCONF or
   RESTCONF users to a preconfigured subset of all available NETCONF or
   RESTCONF protocol operations and content.










Graf, et al.              Expires 26 April 2027               [Page 132]

Internet-Draft     BMP YANG Network Telemetry Message       October 2026


   There are a number of data nodes defined in this YANG module that are
   writable/creatable/deletable (i.e., "config true", which is the
   default).  All writable data nodes are likely to be reasonably
   sensitive or vulnerable in some network environments.  Write
   operations (e.g., edit-config) and delete operations to these data
   nodes without proper protection or authentication can have a negative
   effect on network operations.  The following subtrees and data nodes
   have particular sensitivities/vulnerabilities:

   "There are no particularly sensitive writable data nodes."

   Some of the readable data nodes in this YANG module may be considered
   sensitive or vulnerable in some network environments.  It is thus
   important to control read access (e.g., via get, get-config, or
   notification) to these data nodes.  Specifically, the following
   subtrees and data nodes have particular sensitivities/
   vulnerabilities:

   "There are no particularly sensitive readable data nodes."
